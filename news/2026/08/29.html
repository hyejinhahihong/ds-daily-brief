★01Apple, Agent Seer 공개 — 툴 스펙만으로 AI 에이전트 평가 시나리오 자동 합성Agent Seer: Synthesizing Scenarios from Specification Understanding✍️ 블로그 · machinelearning.apple.comAI 에이전트가 외부 툴을 활용하는 상황을 평가하려면 실제 사용자의 툴 조합 및 대화 반복 방식을 반영한 현실적인 테스트 시나리오가 필요하다.

그러나 이런 시나리오를 수작업으로 만들면 깊은 도메인 전문성이 필요하고 여러 툴 생태계로 확장하기 어렵고, API가 변화해도 갱신되지 않는 정적 벤치마크가 된다. Apple 연구팀은 함수명, 자연어 설명, 타입이 지정된 파라미터 스키마로 구성된 툴 스펙 자체에 이미 현실적인 시나리오를 합성할 충분한 의미 정보가 담겨 있음을 관찰했다. 이를 바탕으로 수동 큐레이션이나 실제 툴 실행 없이도 평가 시나리오를 만드는 Agent Seer를 제안한다.

WHY IT MATTERS

툴 사용 에이전트 평가는 기존에 사람이 직접 시나리오를 설계해야 해 확장성이 떨어지고 API 변화에 취약했는데, 이 문제를 해결하면 다양한 툴 생태계에 대한 지속적이고 자동화된 평가가 가능해진다.

WHAT'S DIFFERENT

기존의 수작업 시나리오 구성 및 정적 벤치마크와 달리, 툴 스펙만으로 실행 없이 시나리오를 자동 합성한다는 점이 다르다.

01Apple 연구, LLM은 베이즈 업데이트를 일관되게 따르지 않는다 — 정보처리 갭으로 확률적 신념의 내부 불일치 측정LLMs Are Not (Consistently) Bayesian: Quantifying Internal (In)consistencies of LLMs’ Probabilistic Beliefs✍️ 블로그 · machinelearning.apple.com이 연구는 LLM을 정보처리 규칙으로 간주하고, 새로운 증거가 주어졌을 때 베이즈 업데이트에서 벗어나는 정도인 '정보처리 갭'을 정의해 LLM의 확률적 신념 업데이트 방식을 분석한다.

의료·과학·법률처럼 정답이 하나로 정해지지 않는 복잡한 영역에서는 AI가 불확실한 신념을 적절히 표현하고 갱신해야 하는데, 저자들은 대규모 실험을 통해 LLM의 신념 업데이트가 내부적으로 일관되지 않음을 정량적으로 보인다. 즉 동일한 증거에도 모델이 서로 다른 방식으로 확률을 갱신하는 불일치가 존재한다.

WHY IT MATTERS

불확실성 하에서 합리적 의사결정을 내려야 하는 고위험 응용 분야에 LLM을 배치할 때, 신념 업데이트의 내부 비일관성은 신뢰성과 안전성에 직접적인 위험 요인이 된다.

WHAT'S DIFFERENT

기존에는 LLM의 출력 정확도나 캘리브레이션을 주로 평가했지만, 이 연구는 LLM을 정보처리 규칙 자체로 취급해 베이즈 업데이트 기준과의 편차를 직접 측정하는 새로운 분석 틀을 제시한다.

01AWS SageMaker Feature Store, BatchWriteRecord·ListRecords API 출시 — 최대 25건 일괄쓰기·레코드 조회 지원Batch write and discover records in Amazon SageMaker Feature Store✍️ 블로그 · aws.amazon.comAmazon SageMaker Feature Store에 BatchWriteRecord와 ListRecords 두 API가 추가됐다.

BatchWriteRecord는 여러 피처 그룹에 걸쳐 최대 25개 레코드를 한 번의 호출로 기록하며, 레코드별 부분 성공 처리와 TTL 설정, 기존 PutRecord와 동일한 EventTime 기반 순서 보장을 유지한다. ListRecords는 Standard(DynamoDB 기반)와 In-Memory(Redis 기반) 저장 계층 모두에서 페이지네이션으로 레코드 식별자를 열거할 수 있게 해준다. 기존에는 초당 1만 건씩 5개 피처 그룹에 기록해야 하는 파이프라인이 초당 5만 건의 개별 PutRecord 호출을 해야 했고, In-Memory 계층은 오프라인 스토어나 Athena 조회 없이 레코드를 조회할 방법이 없어 식별자를 잃으면 데이터가 영구 손실되는 문제가 있었다.

WHY IT MATTERS

고빈도 피처 파이프라인을 운영하는 팀은 API 호출 오버헤드를 줄여 처리량을 크게 높일 수 있고, In-Memory 계층 사용자는 처음으로 저장된 레코드를 열거·복구할 수단을 확보하게 된다.

WHAT'S DIFFERENT

기존 PutRecord가 레코드 1개당 API 호출 1회를 요구해 N×M 방식의 연결 오버헤드를 유발했던 것과 달리, BatchWriteRecord는 여러 피처 그룹에 걸쳐 최대 25건을 한 번에 처리하며 부분 성공을 지원한다.
